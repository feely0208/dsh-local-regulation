# 地方数据条例检查（dsh-local-regulation）

**什么时候用**：项目要核对**上海、深圳**两市地方数据条例的额外要求时。
用户会说：「上海的数据条例有没有踩」「深圳对用户画像 / 数据销毁有什么额外要求」
「这个项目在深圳运营合不合规」「人脸识别场所的显著标识、对外导出的去标识化、
数据安全责任人、数据销毁规程查一下」。

> ⚠️ **第一句话必须先说清楚**：本插件只覆盖上海、深圳两市条例；是否适用取决于实际运营地，
> **需人工确认**。不要用它推断用户的实际运营地，也不要把结论扩大成「全国合规」。

## 怎么用

```bash
<cli 路径> --root <项目目录>       # 检查一个项目
<cli 路径> --demo                  # 用内置样本看 7 条判据的检出效果
<cli 路径> --list-rules            # 列出 7 条判据与条款出处
<cli 路径> --html local.html       # 出 HTML 报告（可截图存档）
```

在会话里最自然的用法：先问一句「这个项目实际运营地在哪、是否包含上海或深圳」，
得到确认后再跑；如果用户明确不在两市，直接说明本插件不适用，不要拿它下结论。

## 它查什么（7 条）

| 规则 | 查什么 | 依据 |
|---|---|---|
| `LR-SH-23` | 人脸识别 / 图像采集场所：显著标识与非唯一验证方式的说明 | 上海市数据条例第二十三条 |
| `LR-SZ-26` | 对外提供个人数据前的去标识化 | 深圳经济特区数据条例第二十六条 |
| `LR-SZ-29` | 用户画像的用途、主要规则与拒绝途径 | 深圳经济特区数据条例第二十九条 |
| `LR-SZ-73` | 敏感个人数据 / 重要数据的安全管理机构与责任人 | 深圳经济特区数据条例第七十三条 |
| `LR-SZ-75` | 数据处理全流程记录与数据来源合法性 | 深圳经济特区数据条例第七十五条 |
| `LR-SZ-79` | 数据共享开放与对外接口的安全管理制度 | 深圳经济特区数据条例第七十九条 |
| `LR-SZ-80` | 数据销毁规程 | 深圳经济特区数据条例第八十条 |

每条规则先用 `when` 限定触发场景（例如只有出现人脸识别能力才查 `LR-SH-23`），
不满足条件的规则会进入报告的 `notApplicable`，既不报也不假装查过。

## 怎么读结果

1. **先确认适用范围**：报告头写着「仅上海 / 深圳 · 适用范围需人工确认」。实际运营地不在两市，
   这些命中基本与你无关；不确定时让用户去问合规/法务，不要替用户猜。
2. **再看「检查规则 N/7 条」**。少于 7 条说明有规则因触发条件不满足而未运行，
   报告会列出是哪几条 —— 这是「不适用」，不是「已通过」。
3. **absence 类命中（位置显示 `**/*`）表示全项目没找到对应说明**，证据里会写检查了多少文件。
   它最多说明「仓库里没有」，不能说明「公司没做」—— 制度可能在内网、线下物料或工单系统里。
4. **命中 ≠ 违规**。报告给的是「值得人工确认的点」：例如 `/me/export` 这类本人查阅导出，
   一般不属于「向他人提供个人数据」；migrations 里的 `DROP TABLE` 也不属于数据销毁。
5. **它不下「安全 / 不合规」结论**，也不承诺「保证通过」。

## 不要做什么

- 不要在没有确认运营地的情况下，把上海/深圳的命中当成全国通用问题
- 不要因为反例 0 命中或报告全绿，就认为「地方合规已经做完」——静态扫描只覆盖可检测的 7 个点
- 不要为了消掉命中，把制度文档塞进仓库就算完成；关键还是制度是否真的执行
- 不要把它当法律意见；涉及处罚风险时找专业律师/合规顾问
